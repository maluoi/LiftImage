# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Lift Image

**Lift Image (`.lfi`)** is a baked image format for real-time engines. On one thread it decodes 1.8 to 15× faster than JPEG, WebP, AVIF and JPEG XL at the same SSIMULACRA2, from files smaller than WebP's and libjpeg-turbo's and the same size as mozjpeg's; JPEG XL is 21% smaller. Lossless is 19% smaller than PNG and decodes over 3× faster. HDR decodes straight to RGBA16F, RG11B10F or RGB9E5, about 6× faster than a .hdr loader, from files about 30× smaller. Every file is a mip chain: any prefix decodes to a smaller mip, so you can show mip 2 while the rest streams in and continue without redoing work. The output is plain pixels for your runtime BC/ASTC encoder, so one asset serves every GPU. It's about 1,800 lines of dependency-free C11, with an integer-only, bit-exact decoder of about 48 KB. Packed material maps get a data mode with no color transform.

Inside: reversible opponent color (luma, red less green, blue less green, by lifting), a 9/3 integer lifting wavelet (5/3's predict, a 4-tap update) in 16-bit lanes over 512x512 tiles, with 4 fractional bits for lossy, deadzone quantization with rate-aware decisions and per-band centroid offsets, chroma detail predicted from luma, and tANS over two interleaved streams that carry each symbol's raw bits inline. The format is specified in `docs/format.md`.

## What matters here

These are budgets, not afterthoughts. A change has to earn its keep against all of them.

- **Decode speed**, single-threaded. The engine's asset pipeline parallelizes across files, so the codec never spawns threads.
- **File size at matched quality**, judged by BD-rate on SSIMULACRA2 for color, with Butteraugli as a check. PSNR, and BC1 PSNR since the output feeds a GPU block encoder, are guards. Gray and normal maps are data, judged by PSNR and angle error.
- **Lines of code and binary size**, for the decoder and the encoder separately. The decoder is about 1,070 lines and 48 KB.
- **Simplicity.** One code path beats two, and a derived value beats a stored one.
- **Small images.** Fixed per-file costs (table builds, headers) dominate 256x256 textures, so check them, not just the big corpus.
- **Determinism.** The decoder is integer-only and must produce identical output on every compiler and platform.

## How we work

- Measure in [LiftImage-lab](https://github.com/maluoi/LiftImage-lab), which clones this repository inside itself and holds the corpus, the benchmark and the checkpoint history. Every landed change gets a checkpoint there; its CLAUDE.md has the workflow.
- Write portable C that gcc and clang both auto-vectorize: 16-bit lanes, branchless selects, `restrict` on row loops. Check clang with `-Rpass-missed=loop-vectorize`, since gcc hides aliasing problems that leave clang scalar. Intrinsics only for a measured, large win. GCC `-O2` skips these loops (4x slower), so the codec builds at `-O3`.
- The entropy loop is register-starved. Small edits can spill its state to the stack, so measure every change there.
- Vectorized cold loops cost kilobytes. Prefer one code path for rare cases, and use `restrict` so compilers skip alias-checked duplicates.
- Tried and rejected, so don't retry without a new reason: two-phase entropy decode, more than two entropy states, neighbor-magnitude contexts, symbols packed into tANS entries, an AVX-512 build, AVX2 color packing, fusing the last wavelet level into color conversion, fast paths for partly zero levels, splitting the color inverse from RGBA packing to share it with HDR (3% faster with AVX2, 6 to 10% slower with SSE2), adaptive quantization by masking or by activity, in either direction.

## Layout

- `src/lfi.h` public API, `src/lfi_internal.h` shared by both coders, `src/lfi_dec.c` and `src/ent_dec.c` the decoder, `src/lfi_enc.c` and `src/ent_enc.c` the encoder. `src/` is the source of truth.
- `dist/lift_image.h` is the single-header library, generated by `tools/amalgamate.py`. Don't edit it by hand.
- `CMakeLists.txt` builds the static library `lift_image` for FetchContent consumers, optimized even in their Debug builds, and the tool and tests when built on its own.
- `tools/lfi.c` is the command line tool (encode, decode, info, verify, hash, thumbnail), built on the single header.
- `plugins/` teaches other software the format, all on `plugins/thumbnail.h`: `linux/` (MIME type, freedesktop thumbnailer for `lfi thumbnail`, and in `kde/` a KIO thumbnailer and Qt image plugin built with CMake), `windows/` (a WIC codec in C, built with CMake; test it under Wine with MSVC) and `macos/` (Quick Look extensions in an app bundle, built with its own Makefile on a Mac). `make install` installs the tool and the Linux files. The codec must compile after `windows.h`, which defines `near`, `far`, `min` and `max` as macros. See `plugins/README.md`.
- `tools/fuzz/` holds libFuzzer harnesses for decoding arbitrary bytes and for encode and decode round trips, plus a seed generator.
- `docs/format.md` is the format spec, and `docs/vectors/` its test vectors. A format change updates both; the lab regenerates the vectors and their hashes. `make test` (or `ctest`) checks the vectors against the spec's table.
- Build with `make -j8`. `make fuzz` builds the fuzzers and seeds `build/fuzz_corpus`, then run `build/fuzz_decode -max_total_time=300 build/fuzz_corpus`.
- Every decoder entry point validates its input and must stay memory safe on any bytes. Fuzz before releases.

## Coding Guidelines

Before writing code, make it clear to the user what code you're working on, and that you're going to work on code. This is especially important if the user has not asked for code.

When writing code, please use the Edit tool! Edit is safer, and lets me observe changes (I enjoy reading the edits!). For changing code algorithmically (mass rename across multiple files), it's okay to use other tools, but be cautious when doing so.

**C**
- Plain C11. C++ or Objective-C only where a platform API forces it, as in the KDE and macOS plugins. No STL, no virtual functions, no operator overloads, no exceptions.
- The codec, meaning everything `tools/amalgamate.py` puts in `dist/lift_image.h`, must also compile as C++11 and with MSVC, in C and C++ modes, warning-free at `-Wall -Wextra -pedantic` and `/W4`. So in the codec: no designated initializers or compound literals (use positional initializers, a named local, or a small helper like `ent_streams`), `memset` rather than `= {0}` for structs, explicit casts on `malloc` and `void*`, `LFI_RESTRICT` rather than `restrict`, and `!= 0` when a flag test becomes a `bool`. Tools and tests stay full C11.
- POD structs only - no constructors, no classes, no default values. Zero-initialized structs should be a valid default state.
- Use `stdint.h` types: `int32_t` not `int`, `uint8_t` not `unsigned char`.
- Outside the codec, use designated initializers for structs, inline at call sites when possible:
  `compile(&(svsl_options_t){ .spirv_version = SVSL_SPIRV_1_3 });`
- Use `//` comments, not `/* */`.
- Use function parameter prefixes for pointers: `opt_` = optional (nullable), `out_` = written to, `ref_` = read and written, const keyword for read only.

**General:**
- **Functional style**: functions should be pure where possible, taking specific arguments rather than whole contexts. Exception: public functions of singleton-like modules.
- **Data-oriented design**: prefer flat arrays and indices over pointer graphs, be aware of memory usage patterns and architect data for cache efficiency. Coding is _data transformation_, not shaping objects.
- **Single source of truth**: caching a value in multiple places is a source of bugs. Derive, don't duplicate. If a cache is genuinely needed, it must be private to one module.
- Prefer simplicity, low indentation, and early-outs.
- Immediate-mode interface design. Keep code stateless where possible.
- Tabs for indentation, spaces for alignment (mix them so alignment holds at any tab width).
- Prefer early returns over deep nesting.
- Vertical alignment of related code is encouraged.
- API names (things developers type) should be short and self-explanatory. Units of measure go in names developers don't type.
- Prefer pure functions when possible, minimize unnecessary function inputs.
- Null checking should be done sparingly, an NRE is very visible and easy to debug. If an item should not be null, it should _not_ be checked for null. If an item can be null, indicate it is _optional_ - this repo's parameter prefixes carry that contract (`opt_`, `opt_out_`, plus `ref_`/`out_` for mutated and output parameters).
- For threading, prefer lock-free techniques and atomics whenever possible. Actual locks are a last resort.
- Non commentdoc comments: delete any that restate the code. Don't use them to preserve the reasoning from the session that produced the code, state what the next reader needs rather than what you learned. What survives that is one line; two only if the second is doing real work. If it needs more, it belongs in the commit message or a doc, not the source. A comment that explains what the code does means the code should be clearer, not that it needs a comment: explain why, or fix the name. Before finishing a change, list every comment in the diff and judge each one. Don't scan for the long ones.

  Too long:
  ```cpp
  // TimedWaitAny legalizes a blocking skr_future_wait, which cubemap lighting
  // and texture readback both need. In a browser that rests on Asyncify, and
  // asking without it fails instance creation outright rather than degrading,
  // so the web build always links -sASYNCIFY.
  ```
  Better:
  ```cpp
  // Asking for this without Asyncify fails instance creation outright
  ```
- Comments in private structs should be short, on the same line as the field.
- Forward function declarations don't get commentdocs. This keeps header files condensed and clean.
- Please avoid free standing - and —, check for run-on sentences.
